# תוכנית עבודה: redis-enterprise-services

**סטטוס:** טיוטה שנייה
**תאריך:** 2026-10-20

## מטרה

שירות FastAPI שמקבל פעולה עסקית אחת על משאבי Redis Enterprise, למשל "צור DB עם שלושה יוזרים", ומבצע אותה
כרצף של קריאות REST API לקלאסטרים.

הביצוע בנוי כ-**Saga**: לכל צעד יש פעולה מפצה. אם צעד נכשל, הצעדים שכבר הצליחו מבוטלים בסדר הפוך,
והקלאסטר חוזר למצב שהיה לפני הפעולה.

## עקרונות

### כל קריאה יוצאת דרך שירות הקצה

השירות **לעולם לא פונה ישירות לקלאסטר**. כל קריאה ל-REST API של Redis Enterprise נשלחת לשירות הקצה,
בפרוטוקול של cluster-relay:

```
POST /
x-cluster-method: GET
x-cluster-url: https://<cluster>:9443/v1/bdbs
x-cluster-authorization: Basic <credentials>
<body כמו שהוא>
```

| שלב | שירות הקצה |
|---|---|
| עכשיו | proxy פשוט ב-docker compose שמעביר כל בקשה כמו שהיא לקלאסטר |
| בהמשך | cluster-relay האמיתי |

ההחלפה מתבצעת בקונפיגורציה בלבד (URL של שירות הקצה), בלי שינוי קוד בסרוויס.

### בלי קוד כפול

כל קריאה ל-API נכתבת פעם אחת בלבד. כדי שזה יתקיים:

- **משאב:** לכל סוג משאב (DB, ACL, role, user) מוגדרות פעולות `create`, `get`, `update` ו-`delete`
  פעם אחת. כל ה-Sagas משתמשים באותן פעולות.
- **צעד ופיצוי:** צעד ב-Saga מורכב מפעולות של המשאב. הפיצוי של `create` הוא אותו `delete` שמשמש את
  Saga המחיקה, והפיצוי של `update` הוא `update` עם ה-snapshot שנשמר לפניו.
- **AA:** Saga של AA מריץ את אותם צעדים על כל אחד מהקלאסטרים המשתתפים. הצעד היחיד שייחודי ל-AA הוא
  יצירה ומחיקה של ה-CRDB.
- **Transport:** יש client אחד לשירות הקצה, וכל הפעולות עוברות דרכו.

### שום ערך בקוד

כל ערך שהשירות צריך נטען ממקור חיצוני, ואפשר לשנות אותו בלי לבנות את הקונטיינר מחדש: defaults, רשימת
הקלאסטרים, שדות DB שאי אפשר להחזיר, זמני המתנה, מדיניות retry, timeouts, שמות headers ורמות לוג. בקוד אין
ערכים. ב-Kubernetes המקור הוא ConfigMap או Secret, ומקומית קבצים ב-`config/` ו-`.env`.

### Vertical slicing

כל שלב הוא פיצ'ר שלם מקצה לקצה (API, Saga, צעדים, פיצוי, טסטים). שלב נחשב גמור רק כשהוא עובד מול קלאסטר
אמיתי דרך שירות הקצה. לא בונים מראש קוד שמשרת רק שלבים עתידיים, אבל המבנה מאפשר להוסיף אותם בלי לשכפל קוד.

## סוגי כניסה לשירות

| כניסה | מה היא עושה | rollback |
|---|---|---|
| פעולות עסקיות | בקשות מה-UI (10–15 שדות + defaults), מפורקות ל-Saga | כן |
| קריאה ישירה לקלאסטר | קוד קלאסטר + method + path + body, מועברים כמו שהם. לשדות ולפעולות שה-UI לא חושף. | לא |
| פעולה ספציפית | route ייעודי לפעולה מסוימת. יוגדר בהמשך. | ייקבע |

כל הכניסות משתמשות באותו תרגום קוד קלאסטר לכתובת ובאותו client לשירות הקצה.

**הקריאה הישירה לא מוגבלת:** כל method וכל path מותרים. היא קיימת בשביל מה שלא תוכנן מראש.

**הזדהות חובה בכל route:** זו ההגנה של השירות. השיטה (טוקן או שם משתמש וסיסמה) תיקבע בהמשך, ולכן היא
מאחורי ממשק אחד שמוחל על כל ה-routes. החלפת השיטה לא נוגעת ב-routes עצמם. ההזדהות מול השירות נפרדת
מפרטי הגישה לקלאסטרים.

## משאבים בשלב 1–2

נבדק מול `docs/reference/redis-rest-api/`.

| משאב / יכולת | API | הערה |
|---|---|---|
| DB | `bdbs` | |
| CRDB | `crdbs` | הבקשה כוללת URL, FQDN ופרטי גישה לכל קלאסטר משתתף |
| ACL, role, user | `redis_acls`, `roles`, `users` | ביוזר משתמשים רק ב-`role_uids`, לא בשדה `role` המיושן |
| חיבור role ↔ ACL ל-DB | שדה `roles_permissions` ב-`PUT /v1/bdbs/{uid}` | צעד נפרד עם פיצוי. ב-AA השדה לא קיים ב-CRDB, ולכן מעדכנים כל bdb מקומי (לפי `local_databases`) |
| מעקב אחרי פעולות ארוכות | `crdb_tasks`, `actions` | ב-`crdbs` אפשר לקבוע את מזהה ה-task (`X-Task-ID`), וכך לברר מה קרה אחרי timeout |
| פרטי קלאסטר | `cluster` | FQDN של הקלאסטר, נדרש ליצירת CRDB |

- **`default_user`:** ברירת המחדל של Redis היא `true`, כלומר DB חדש פתוח ליוזר `default`. ב-defaults שלנו הוא כבוי.
- **סנכרון AA:** הבקשות עוברות דרך שירות הקצה, אבל הסנכרון בין הקלאסטרים רץ ישירות ביניהם.

## סביבת הבדיקות (docker compose, זמני)

| שירות | עכשיו | לפני שלב 2 |
|---|---|---|
| קלאסטר Redis Enterprise | אחד | שניים |
| proxy (שירות קצה זמני) | אחד | אחד |
| אתחול קלאסטר (bootstrap) | אוטומטי, דרך REST API | לכל קלאסטר |

הקלאסטר מבוסס על `redislabs/redis`, עם `cap_add: sys_resource` ופורטים 8443, 9443 ו-12000+.

## שלבים

### שלב 1: יצירת DB על אתר בודד

זה ה-walking skeleton. בשלב הזה נבנים לראשונה כל הרכיבים:

1. שלד הפרויקט: uv, ruff, pytest, pre-commit, Settings ולוגים.
2. docker compose: קלאסטר אחד ו-proxy.
3. client לשירות הקצה.
4. משאבים: DB, ACL, role, user.
5. מנוע ה-Saga: הרצת צעדים, ובכשל הרצת פיצויים בסדר הפוך.
6. Endpoint ליצירת DB.

| # | צעד | קריאה | פעולה מפצה |
|---|---|---|---|
| 1 | יצירת DB | `POST /v1/bdbs`, ואז המתנה ל-`status: active` | `DELETE /v1/bdbs/{uid}` |
| 2 | לכל יוזר: ACL | `POST /v1/redis_acls` | `DELETE /v1/redis_acls/{uid}` |
| 3 | לכל יוזר: role | `POST /v1/roles` | `DELETE /v1/roles/{uid}` |
| 4 | לכל יוזר: user | `POST /v1/users`, עם `role_uids` | `DELETE /v1/users/{uid}` |
| 5 | חיבור ל-DB | `PUT /v1/bdbs/{uid}` עם `roles_permissions` (role ↔ ACL) | החזרת `roles_permissions` הקודם |

**הגדרת "גמור":**
- `POST` ל-endpoint יוצר, דרך ה-proxy, DB עם N יוזרים, ואפשר להתחבר ל-DB עם כל אחד מהם.
- כשל מוזרק בכל אחד מהצעדים משאיר את הקלאסטר נקי.

### שלב 2: יצירת Active-Active

- הקלאסטר השני נוסף ל-docker compose.
- ה-DB נוצר דרך `POST /v1/crdbs`, והמשימה האסינכרונית נמתנת דרך `/v1/crdb_tasks/{task_id}`.
  הפעולה המפצה היא `DELETE /v1/crdbs/{guid}`.
- ACL, roles ו-users נוצרים על כל אחד מהקלאסטרים המשתתפים, באותם צעדים של שלב 1.
- **כשל חלקי:** צריך לטפל במצב שבו הצעד הצליח בקלאסטר אחד ונכשל בשני.

### שלב 3: מחיקה

- מחיקת DB (אתר בודד ו-AA) יחד עם היוזרים, ה-roles וה-ACLs שנוצרו בשבילו, באותן פעולות `delete`
  שמשמשות כפיצוי בשלבים 1 ו-2.
- **מה מפצים כשמחיקה נכשלת באמצע?** האפשרויות הן ליצור מחדש, או להמשיך קדימה (forward recovery).
  נדרשת החלטה.

### שלב 4: עריכה

- הוספה והסרה של יוזרים, שינוי הרשאות ושינוי הגדרות DB (זיכרון, persistence וכו').
- לפני כל `update` נשמר snapshot דרך `get`, והפיצוי מחזיר אותו.

### אחרי שלב 4: מעבר ל-cluster-relay

ה-proxy ב-docker compose מוחלף ב-cluster-relay. כל הטסטים של שלבים 1–4 צריכים לעבור בלי שינוי קוד בסרוויס.

## תוצאה לא ידועה של צעד

יש מצבים שבהם הצעד נכשל מבחינת ה-Saga, אבל ייתכן שהפעולה בוצעה בקלאסטר:

| מצב | מה קרה בפועל |
|---|---|
| `response_rejected` על פעולת כתיבה | הקלאסטר ביצע את הפעולה (למשל יצר DB), אבל cluster-relay חסם את התשובה. ה-Saga לא קיבל את ה-`uid`. |
| `cluster_unreachable` בגלל timeout | הבקשה אולי הגיעה לקלאסטר ובוצעה. אי אפשר לדעת. |

**המשמעות:** פיצוי לא יכול להסתמך רק על ה-`uid` שחזר בתשובה. לכל משאב חייב להיות שם דטרמיניסטי שנגזר
מהבקשה, והפיצוי מאתר את המשאב לפי השם הזה ומוחק אותו אם הוא קיים. מכאן ששאלות 5 ו-6 קריטיות כבר בשלב 1.

## דרישות מ-cluster-relay

שינויים שנדרשים בשירות הקצה כדי שה-Saga יוכל לקבל החלטות נכונות. עדיין לא מומשו, ונדרשת החלטה של
הבעלים של cluster-relay.

| # | דרישה | למה |
|---|---|---|
| R1 | סימון חד-משמעי של שגיאות שה-relay עצמו יצר, למשל header ייעודי ש-cluster-relay מוסיף רק לתשובות שלו | שגיאה של הקלאסטר עוברת עם ה-status המקורי שלה, ולכן 502 מהקלאסטר נראה בדיוק כמו 502 של ה-relay |
| R2 | הבחנה בין timeout (אולי בוצע) לבין כשל חיבור (בוודאות לא בוצע) | רק במקרה של timeout ה-Saga צריך לבדוק אם המשאב נוצר |
| R3 | ב-`response_rejected` ייתכן שה-relay צריך להחזיר את ה-status המקורי של הקלאסטר | כך ה-Saga יודע שפעולת הכתיבה הצליחה, גם בלי לקבל את ה-body |
